# 跨机器打包的服务地址可靠性方案

日期：2026-11-13。状态：研究方案，新增机制尚未实施。

## 目标与已确认的事实

同一份代码在 Windows、macOS、CI 或 IDE 中构建，未指定环境时都使用正式服务 `https://api.vincent-tech.cn/v1`。正式包误传其他编译期地址必须失败，不能依赖打包人的记忆。保留 App 内手动修改地址，并显示当前地址的来源。

本次检查确认：

- 原 `lib/data/sources/api_base_url.dart` 通过 `String.fromEnvironment` 读取 `API_BASE_URL`，缺省值是 `http://localhost:8787/v1`。
- 本机已有的 `0.8.51+68` APK 的 `lib/arm64-v8a/libapp.so` 包含上述 localhost 地址，不包含正式地址。
- 原 APK CI、Android README 和 iOS 重新打包命令没有指定地址；旧的发布记录已使用正式域名。
- 正式服务 `/v1/health` 返回 HTTP 200 和 `{"ok":true,"service":"global_village_server"}`。
- `SettingsStore.apiBaseUrl` 的优先级是已保存地址、编译期默认值；账号、同步、诊断和内容下载共同读取这项设置。
- `.trae/publish_apk.py` 只检查源 APK 是否存在，再按当前 `pubspec.yaml` 命名，没有核对包内版本、环境、地址或构建来源。构建失败后仍可能把旧包作为新版本发布。
- 本机 Flutter 是 `3.47.5`，CI 配置是 `3.35.4`。这不是地址错误的直接原因，但构建环境也需要统一。

## 方案比较

| 方案 | 能解决的问题 | 剩余问题 |
| --- | --- | --- |
| 修改默认地址并补齐构建命令 | 不传参数时连接正式服务，改动小 | 误传参数仍能生成错误包；旧产物仍能被复制发布 |
| 仓库统一配置、编译期约束、统一构建与发布校验 | 覆盖参数遗漏、参数错误、入口差异和旧包误发 | 需要增加构建工具、配置测试和产物验证 |
| Android/iOS 完整 flavors 或远程配置服务 | 适合长期维护多个独立环境，或远程切换服务 | 原生配置和签名维护增加；远程配置自身仍需要可信初始地址 |

推荐第二种。当前项目无需先引入远程配置服务；后续存在独立测试服务时再扩展原生 flavors。

## 1. 服务地址只在仓库定义一次

增加不依赖 Flutter UI 的纯 Dart 配置模块，例如 `lib/core/app_environment.dart`。App 和 `tool/build_release.dart` 共同导入，正式域名只在该模块维护。

保留 `lib/data/sources/api_base_url.dart` 作为现有客户端的兼容出口，避免各 API 分别管理地址。

配置规则：

- `APP_ENV` 缺省为 `production`，与 Flutter 的 debug/profile/release 模式分别处理。不要把 release 自动理解为另一个业务环境。
- `production` 的内置默认地址固定为正式地址。`API_BASE_URL` 为空或与正式地址一致可通过；其他值编译失败。
- `development` 必须显式选择，允许显式指定局域网或本机服务地址。构建工具校验 URL 的协议、主机和 API 路径。
- 不认识的环境名直接失败，例如拼错的 `prodution`。
- 正式域名迁移通过提交配置变更完成，不能在某台机器的私有配置里覆盖正式域名。

不能只在构建脚本检查参数，因为 IDE 或直接执行 `flutter build` 可以绕过脚本。约束必须由 App 实际使用的编译期常量触发。

### 已完成的可行性验证

临时纯 Dart 实验使用 const 构造函数约束环境和正式地址，再由主程序读取该常量。执行 `dart compile exe`，没有启用运行时 assertions：

| 输入 | 实测结果 |
| --- | --- |
| 无环境、无地址参数 | AOT 编译成功，执行输出正式地址 |
| 默认正式环境，误传 localhost | 常量求值失败，AOT 编译退出码 254 |
| development，显式传入本机地址 | AOT 编译成功，执行输出指定地址 |
| 拼错环境名 | 常量求值失败，AOT 编译退出码 254 |

这是编译期 const 约束，不是正式版可能关闭的普通运行时 `assert()`。实验位于忽略目录 `.trae/tmp/server-config-research/`，不属于生产实现。落地时仍需验证 Flutter Android AOT 和 iOS AOT 的完整构建行为。

## 2. 本地与 CI 共用构建入口

提供跨平台 Dart 命令，以下为计划接口：

```text
dart run tool/build_release.dart apk --environment production
dart run tool/build_release.dart ipa --environment production
```

构建工具从统一模块取得配置，校验 SDK 和环境，执行 Flutter，检查成功结果，再生成带包文件摘要的构建记录。CI 调用同一入口，不再复制业务域名。iOS 构建仍需 macOS 和相应签名环境。

在仓库记录支持的 Flutter SDK 版本，让本地工具和 CI 共同读取。地址正确性由配置与编译约束保证；SDK 固定用于减少机器间编译差异。目标是环境和服务地址一致，不要求不同机器生成字节完全一致的包。

## 3. 发布操作验证实际产物

将构建和发布串成一个失败即停止的流程。只有本次构建成功、产物验证通过，才更新 APK 下载文件与二维码。原发布工具不得继续接收任意已有 `app-release.apk` 并按源码版本改名。

构建记录至少包含：应用版本与 build number、Git 提交、源码是否有未提交修改、业务环境、内置默认地址、SDK 版本、本次构建标识和包文件 SHA-256。

发布前必须核对：

1. 包内应用标识和版本与预期一致。
2. 本次构建标识与构建记录一致，环境为 production。
3. 记录中的包文件 SHA-256 与待发布文件一致。
4. App 实际使用的配置与记录一致，而不是只核对脚本生成的记录本身。

包内构建信息应与 App 使用的编译配置关联。只写一个外置 JSON，或只往 APK 放一个配置说明文件，都不足以证明实际请求地址正确。

二进制字符串检查可作为快速辅助，但不能作为唯一证明：编译优化可能改变字符串存放形式。CI 的产物冒烟测试应启动构建后的 App，读取由同一配置模块输出的环境、内置地址和构建标识，并验证匿名健康请求的目标；无需登录账号。Android 使用模拟器，iOS 使用适用的 macOS 测试流程。IPA 最终签名产物仍需核对包信息和摘要。

健康检查验证连通性，不负责选择服务地址。正式服务暂时不可达时，不得自动回退到 localhost 或另一台服务器。

## 4. 保留手动地址，明确区分来源

用户已确认：正式版保留服务地址修改入口，区分默认配置与手动设置。

- 默认地址由当前构建的统一配置动态提供，不写入用户设置。
- 只持久化手动覆盖值；来源从“是否存在覆盖值”判断，不从地址字符串猜测。
- 对话框显示“内置默认地址”“当前生效地址”“来源：默认配置／手动设置”。
- 手动保存与默认地址相同的值、或点击“恢复默认”，均清除覆盖值，状态回到默认配置。
- 升级时，无覆盖值的设备自动使用新默认值。旧版保存的非空覆盖值按手动设置兼容，不能因域名看起来旧就擅自删除。
- 保持现有更换服务时退出在线会话的行为，避免把旧服务的会话继续用于新服务。
- 在线会话同时保存其业务环境与规范化服务地址。启动时，在 `AuthController` 自动刷新凭据和同步之前核对绑定地址与当前生效地址；不一致时使在线会话失效并要求重新登录，不能先向新地址发送旧 refresh token。默认域名随升级变化也必须经过此检查，不能只依赖地址对话框的退出逻辑。
- 当前 `SecureTokenStore` 只保存全局 refresh token，没有地址绑定。首次引入绑定时，旧的未绑定凭据无法可靠确定来源，应使其失效并要求在线用户重新登录一次；保留手动地址、本地账号和学习数据。已绑定且地址未变化的会话继续正常恢复。
- 诊断信息同时记录环境、内置默认地址、当前地址、来源和构建标识，便于区分打包问题与手动设置问题。

编译期约束保证正式包的内置地址正确；用户主动设置其他地址是保留的产品功能。两者需要分别识别和验证。

## 5. 验收标准

| 场景 | 预期 |
| --- | --- |
| 新机器拉取仓库，直接构建，未指定环境与地址 | 内置正式地址 |
| 默认或显式正式环境，误传 localhost、局域网、临时隧道或其他域名 | 编译失败，不更新下载文件 |
| IDE、直接 Flutter 命令绕过统一工具 | 编译期规则仍生效 |
| 显式 development 并指定有效调试地址 | 可正常开发与调试 |
| 未识别的环境 | 编译失败 |
| 构建失败，目录里残留上次成功的 APK | 发布失败，原下载包保持不变 |
| 错包、包版本不一致、摘要不一致或记录不是本次构建 | 发布失败 |
| 新安装，无手动覆盖 | 地址来源显示默认配置 |
| 升级，无手动覆盖 | 自动使用当前版本的默认地址 |
| 手动设置、重启、升级 | 保留手动覆盖并显示来源 |
| 升级更换默认地址，旧在线会话仍在 | 在任何自动刷新或同步请求前核对绑定；地址不一致则要求重新登录，不发送旧凭据 |
| 首次迁移没有地址绑定的旧在线凭据 | 重新登录一次，保留地址设置和本地学习数据 |
| 已绑定会话，升级后实际服务地址未变化 | 正常恢复在线会话 |
| 恢复默认 | 清除覆盖，账号、同步、诊断、内容共同使用默认地址 |
| Windows 与 macOS 构建同一源码 | 业务环境和内置默认地址一致 |

## 落地顺序

先完成统一配置与编译期防错，保留现有客户端接口；再完成设置来源和升级兼容；最后接入统一构建入口、包信息与发布校验，增加 CI 产物冒烟测试。

此前的默认地址修复和请求回归测试属于基础修复。本文件描述的编译约束、统一构建工具和发布校验需要后续实现，不能以基础修复通过测试代替完整方案验收。
