# 全自动软件迭代（缺陷闭环）设计

日期：2026-10-24  
状态：已评审待实现

## 目标

在开发者本机在线时，自动完成：**拉取用户反馈 → 只修复明确缺陷 → 测试通过 → commit 并 push 到 `main` → 打包并局域网共享**。

不做功能建议、不做大重构、不做「信息不足」的猜测修复。

## 决策摘要

| 项 | 选择 |
|----|------|
| 自动化程度 | 全自动（有明确缺陷就修，修好就打包共享） |
| 反馈范围 | 仅明确缺陷（崩溃、同步、播放、后台显示错误等） |
| 触发节奏 | 本机每约 20 分钟轮询一次 |
| 代码落库 | 自动 commit 并 **直接 push `main`** |
| 落地形态 | 本机定时 Agent Loop（方案 A） |

## 架构

本机常驻「迭代守护」对话：

1. 定时唤醒（约 20 分钟；启动时立即跑一轮）
2. 若无新的、可判定的明确缺陷 → 写一行跳过摘要后结束本轮
3. 若有 → 分类 → 改代码 → 跑测试 → 版本号 +1 → commit + push `main` → 按现有流程打包共享 → 标记反馈已处理 → 对话摘要

硬规则：

- 功能建议不改代码
- 复现不清不改代码
- 测试失败不 commit / 不 push / 不打包
- 不碰 `tools/.cache`
- **单轮只处理 1 个**最高优先级缺陷

## 组件与数据流

| 组件 | 职责 |
|------|------|
| 本机 Loop（约 20 分钟） | 定时唤醒本对话中的 Agent |
| 反馈源 | Admin API 拉取 `client_reports`（Bearer `ADMIN_TOKEN`，主机 `https://api.vincent-tech.cn`） |
| 已处理标记 | 本机状态文件记录已处理的 `report_id`，避免重复修同一条 |
| 修复 Agent | 分类 → 改代码 → 测试 → bump → commit/push `main` |
| 打包 | 现有 `.trae/publish_apk.py`，`API_BASE_URL=https://api.vincent-tech.cn/v1` |
| 产出 | 对话摘要 + 局域网 APK URL |

成功路径：新缺陷 → 修复且测试通过 → push → 打包共享 → 标记 `report_id`。  
空转路径：无新缺陷 / 全是建议 / 信息不足 → 仅摘要「本轮跳过」。

## 分类规则

**修（明确缺陷）**

- 崩溃、闪退、白屏
- 同步失败或数据明显错误
- 音频/梵文等播放失败
- 管理后台显示错误（缺设备信息、时间非最新等可复现的显示 bug）
- 用户描述中带明确「坏了 / 不行 / 错误 / 打不开」且指向已有功能

**跳过**

- 功能建议、新需求、体验偏好（「希望增加…」「能不能改成…」）
- 信息不足、无法定位模块或无法复现
- 已处理过的 `report_id`
- 工作区已有**非本轮**未提交脏改动（避免踩手改）

跳过时在摘要写明原因，不改代码。

## 门禁

1. 拉反馈失败或无 `ADMIN_TOKEN` → 本轮失败摘要，不改代码
2. 选定缺陷后实现；改动范围必须能追溯到该反馈
3. 运行相关测试（至少：受影响的 Flutter 测试；若改 server，则 `server/` 下相关测试）
4. 测试失败 → 丢弃或回滚本轮未提交改动；将该 `report_id` 标为「需人工」；不 commit / 不打包
5. 测试通过 → bump `pubspec.yaml` / `constants` 版本 → commit（说明为何修）→ `git push origin main`
6. 打包共享；对话输出 APK 局域网链接与本轮摘要
7. 将 `report_id` 写入已处理状态（成功或「需人工」均记录，避免死循环）

禁止：

- 与反馈无关的重构、依赖大升级、格式化全库
- force-push、改 git config、跳过 hooks
- 把 `ADMIN_TOKEN` 或密钥写入仓库或对话摘要

## 状态文件

建议路径（不入库或仅入库模板）：

- `tools/auto_iteration/state.json`（gitignore）记录：
  - `processed`: `{ report_id: { status, at, note } }`
  - `last_run_at`
- 可选：`tools/auto_iteration/PROMPT.md`（入库）作为每轮 Agent 固定指令，便于 `/loop` 引用

## 运维

| 动作 | 说法 / 行为 |
|------|-------------|
| 启动 | 「开始自动迭代」→ 立即跑一轮，再挂约 20 分钟 loop |
| 停止 | 「停止自动迭代」→ 取消 loop |
| 凭据 | `ADMIN_TOKEN` 只读本机环境或 `server/.env`，永不提交 |

前置条件：本机 Cursor 会话可用、Flutter/Java 打包环境可用、能访问 `api.vincent-tech.cn`、局域网分享端口可用。

## 非目标

- 云端独立完成 APK 与局域网共享
- 自动处理功能建议或产品规划
- 自动合并冲突、自动 rebase 他人改动之外的复杂 git 手术
- 修改 Cursor / 系统全局配置以外的「永久守护进程」安装（首版用会话内 loop）

## 验收标准

1. 启动后无新缺陷时，约 20 分钟内出现「本轮跳过」类摘要且无代码变更
2. 投入一条明确缺陷反馈后，某一轮内出现修复 commit（已 push `main`）+ 新 APK 共享链接
3. 投入一条功能建议后，被跳过且不产生 commit
4. 故意让测试失败时，无 push、无新 APK，反馈进入「需人工」
5. 同一 `report_id` 不会被无限重复修复

## 实现顺序（供后续 plan）

1. 状态文件 + gitignore + 每轮固定 PROMPT
2. 反馈拉取与分类辅助（脚本或 Agent 步骤说明）
3. 接线：测试 → bump → commit/push → `publish_apk.py`
4. 文档：如何启动/停止自动迭代
5. 试跑一轮空转 + 一轮（或模拟）缺陷闭环
